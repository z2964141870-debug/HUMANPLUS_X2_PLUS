## 协作规则

流程只有一条：**派一阶段 -> 执行 -> 汇报并等待审核 -> 用户和审阅方讨论 -> 用户派下一阶段。**

- 一次只执行一张已派发的阶段任务；完成后不能因“下一步很明显”自行继续。
- 每次汇报必须说明实际做了什么、证据在哪里、当前停在哪里。自测通过不等于用户审核通过。
- 阶段状态只用：`未派发 / 执行中 / 待审核 / 需补证据 / 阻塞 / 审核通过`。审核通过只能由用户明确确认后登记，不能由执行人或其 Agent 自批。
- 每次新派工写清目标、允许修改的范围、禁止事项、验收证据和结束状态。用户未明确选择的新 checkpoint、PD、planner、固件、架构不得自行替换。
- 同一原因连续失败两次，或约 20 分钟仍没有新增诊断证据，就做一次阻塞汇报；说明已经排除什么、剩下哪一个问题，不堆无关参数尝试。
- 任何异常动作、反馈断流、控制归属不清，立即按已验证的安全流程处理并汇报，不等到阶段结束。不通过重启代理绕过 LOCKOUT，不通过放宽保护把失败改成“通过”。
- “汇报后暂停”指不开展下一阶段，不是承重时杀控制进程。涉及真机的任务必须预先约定安全结束/等待状态，现场操作者持续负责；不能让机器人留在无人看护的自定义带电控制下等待线上答复。
- 文档审核不是现场接管授权。带电操作仍需当次物理安全确认、单 writer、反馈新鲜度及仓库操作规范；本卡不授权重启、停 MC、发布 HAL 或升级固件。

## 每次汇报的固定格式

聊天正文尽量控制在 20 行左右；长日志另附完整文件。以下模板每一项都填，没有执行写“未执行”，不知道写“未知”，不写推测结果：

```text
【X2 阶段汇报】
阶段/任务编号：P__ / T__
本轮目标：
执行位置：主机名、角色、目录（不要填密码）
版本身份：源码提交+本地改动；binary/model/config SHA-256 或 manifest 路径
实际操作：关键命令、修改的文件；没有改的关键项
验收结果：逐项 PASS / FAIL / 未测，附关键数字
证据：完整日志/测试输出/manifest/视频文件或可访问链接
异常/未知项：
最后状态：仿真进程是否退出；若涉及真机，支撑/Policy/MC/writer/现场负责人
自评：完成待审核 / 需补证据 / 阻塞（不是“审核通过”）
建议下一步：一句话，只建议，不执行
已停止扩展操作，等待下一张任务卡。
```

证据要求：

- “编译成功”须附命令、退出码和实际产物哈希；“用了新模型”须附实际加载日志和文件哈希，不能只贴启动命令。
- “50/250 Hz”须区别配置值和实测值；“停止成功”须有输入释放/丢失到实际静止/保持的过程，不只是没有报错。
- 所有关键命令保持完整，可遮盖密码/token；不要只截终端最后一句 PASS，不要丢弃失败日志。
- 不能只给另一个人机器上的本地路径。需附实际小型文本文件，或已授权上传后的可访问 GitHub 链接/提交及路径；大权重/视频按存储规则登记，未上传明确标注。
- 每轮保存一份 `reports/experiments/日期_阶段_尝试编号.md`；纯终端文本进 `logs/`，小型 manifest 进 `data/`。这只是命名约定，不要求本轮创建空文件。未经用户要求不 commit/push，不删除原件。

## 审阅与下一轮派工

用户把上述汇报及证据转回本会话后，审阅结论用以下三种之一：

| 结论 | 后续动作 |
| --- | --- |
| 通过 | 列出证据确实证明的范围；用户确认后登记“审核通过”，另发下一阶段任务 |
| 补证据 | 不推翻已有结果；只要求缺少的文件/测量，不重复整轮实验 |
| 退回修改 | 指出具体失败点；下一轮只修该点，保留原始失败记录 |

每张新任务卡沿用：

```text
【X2 下一轮任务】
任务编号/阶段：
上一轮结论和证据：
本轮唯一目标：
允许做：
禁止做：
验收项和需要提交的文件：
完成/失败时的安全结束状态：
停止点：提交阶段汇报后，等待用户明确派下一轮。
```

更改模型、plant、观测变换、底层 IO 或输入停止语义时，须说明哪些已有证据受影响并定向复测，不整套清零，也不沿用失效的旧通过记录。
